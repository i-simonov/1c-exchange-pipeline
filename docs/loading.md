# Загрузка сообщений и очереди

Ядро содержит четыре регистра сведений:

| Регистр | Назначение |
| --- | --- |
| `КОД_ВходящаяОчередьСообщений` | Сообщения, ожидающие запуска сценария загрузки |
| `КОД_ОшибкиЗагрузкиСообщений` | Исходные сообщения, ошибки и повторные попытки загрузки |
| `КОД_ОтложенныйПроцессинг` | Задания записи, проведения, распроведения и установки пометки удаления |
| `КОД_ИсходящаяОчередьСообщений` | Подготовленные сообщения для внешнего транспорта |

У регистров доступны команды открытия списков. Для входящей очереди, ошибок
и процессинга перенесены формы ручного запуска. Форма ошибок позволяет
просмотреть и исправить сообщение, повторить загрузку и взять запись на контроль.

## Подключение загрузки

В модуле `КОД_ДиспетчерЗагрузкиСообщенийПереопределяемый` задаются три точки
интеграции:

- `РеестрыСценариевПоОтправителям` — соответствие строкового кода отправителя
  метаданным обработки с прикладными сценариями;
- `ПриОпределенииУзлаОтправителя` — поиск узла своего плана обмена;
- `ПриПолученииОбъектаОбработки` — необязательная замена экземпляра обработки.

В поставке core эти процедуры не содержат прикладных привязок. Неизвестный
отправитель приводит к ошибке загрузки; исходное сообщение сохраняется для
повторной попытки после настройки интеграции.

Обработка реестра предоставляет экспортную функцию
`РеестрКонвейеровРегистрации()`. Это действующее имя интерфейса также для
реестров загрузки. Функция возвращает соответствие: тип сообщения → массив
сценариев. Минимальный сценарий содержит `Конвейер` и `Обработчики`:

```bsl
Функция РеестрКонвейеровРегистрации() Экспорт

    Обработчики = Новый Массив;
    Обработчики.Добавить(Метаданные.Обработки.МойЗагрузчик);

    Сценарий = Новый Структура;
    Сценарий.Вставить("Конвейер",
        Метаданные.Обработки.КОД_КонвейерОбработчиковЗагрузкаБазовый);
    Сценарий.Вставить("Обработчики", Обработчики);

    Сценарии = Новый Массив;
    Сценарии.Добавить(Новый ФиксированнаяСтруктура(Сценарий));

    Реестр = Новый Соответствие;
    Реестр.Вставить("order", Сценарии);
    Возврат Реестр;

КонецФункции
```

Входящее сообщение содержит `НомерСообщения`, `Идентификатор` (UUID),
`Заголовки`, `Отправитель`, `ТелоСообщения`, `ТипСообщения` и `ДатаВремя`.
Базовый конвейер разбирает тело как JSON. Правила сопоставления JSON прикладным
объектам и границы транзакции их записи реализует прикладной загрузчик.

Штатный запуск:

```bsl
КОД_ДиспетчерЗагрузкиСообщений.ПрочитатьВходящуюОчередьСообщений();
КОД_ПовторнаяЗагрузкаСообщений.ОбработатьРегистр();
```

Константа `КОД_ПорцияЗагрузкиСообщений` задаёт размер порции входящей очереди;
при нуле используется 100. Повторная загрузка по умолчанию обрабатывает порции
по 100 записей с пределом в 5 попыток. Ручная команда формы ошибок позволяет
принудительно повторить обработку отдельной записи.

## Отложенные операции

`КОД_ОбъектыОтложеннойОбработки` — точка настройки состава ссылочных типов.
В core разрешены ссылки на документы и справочники; при внедрении состав можно
сузить. В demo перечислены только его четыре прикладных типа. Этот определяемый
тип не перезаписывается скриптом синхронизации core → demo.

Задание регистрируется в транзакции записи объекта:

```bsl
КОД_ОтложенныйПроцессинг.Зарегистрировать(
    Объект.Ссылка, Перечисления.КОД_ВидыОбработкиДокументов.Запись);
```

Исполнение выполняется вне внешней транзакции:

```bsl
КОД_ОтложенныйПроцессинг.ОбработатьРегистр();
```

Очередь упорядочена по `МоментПостановки` в миллисекундах, затем по ссылке
и виду обработки. Для совпавших моментов порядок определяется этими дополнительными
полями; отдельного глобального счётчика нет. Новая постановка обновляет момент,
сбрасывает ошибку и число попыток.

Шесть подписок `КОД_ОтложеннаяОбработка*` / `КОД_ОтложенноеПроведение*`
снимают выполненные или уже неактуальные задания при записи, проведении,
распроведении и удалении объектов. Проверка прикладного запрета проведения
остаётся в `КОД_ПодпискиНаСобытияПереопределяемый.ДокументЗакрытДляОтложенногоПроведения`.
По умолчанию она возвращает `Ложь`.

## Исходящая очередь и граница транспорта

`КОД_Обработчик_ОтправительСообщенияВОчередь` — готовый Output-обработчик.
Он сохраняет тело, заголовки и получателей в `КОД_ИсходящаяОчередьСообщений`.
Он использует получателей, подготовленных предыдущими этапами, и не содержит
привязки к конкретному плану обмена.

Чтение исходящей очереди внешним транспортом, подтверждения доставки и защита
от повторной доставки подключаются отдельно. Наличие очередей и повторных
попыток загрузки не означает гарантию однократного выполнения бизнес-операции.

## Состав поставки и перенос существующей demo-базы

В core входят регистры с формами и командами, диспетчер загрузки, базовый
конвейер загрузки, повторная загрузка, отложенный процессинг, его перечисления,
подписки, размер порции и три регламентных задания. Задания поставляются
отключёнными; включать их следует после настройки прикладной интеграции.

В demo остаются планы обмена, реестры сценариев, JSON-загрузчики заказов,
складов и товаров, бизнес-правила, начальное заполнение и необязательная
JSON Schema валидация с внешней компонентой.

При переносе из имён очередей, Output-обработчика и подписок удалён префикс
`Демо_`; UUID объектов и их дочерних метаданных сохранены. Обновляйте существующее
demo-расширение полной загрузкой файлов, затем выполните проверку конфигурации
и проверку обновления базы в Конфигураторе. Не удаляйте и не создавайте очереди
заново. После проверки заново выгрузите исходники для обновления `ConfigDumpInfo.xml`.
